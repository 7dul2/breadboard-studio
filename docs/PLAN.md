# Breadboard Studio：面向人和 Agent 的面包板设计平台

状态：开发执行计划（本仓库按此计划实现；本地绝对路径已脱敏）。适用于交给另一个会话通过 `/goal` 执行。

## 1. 目标与交付边界

构建可在浏览器中使用、可本地运行、最终在用户 GitHub 账户公开开源的面包板布局平台。人可以拖放和接线；Agent 可以通过结构化 DSL 与 CLI 完成同样操作，不依赖截图定位或模拟鼠标点击。

主要使用场景：为 ESP32 桌面设备以及 XIAO 环境采集节点，提前规划真实面包板上的元件位置、导线和可达插孔，然后照图搭建。核心价值是物理布局与连接关系准确、设计可以复现和校验。

默认项目名与仓库名：`breadboard-studio`。默认代码许可证：MIT。默认界面中文，标识符和代码采用清晰的英文名称；设计文件字段使用 snake_case。上述默认项可被用户后续指令修改。

本次目标是可使用的 v0.1，不是落地页、演示动画或只有静态画面的原型。最终需要真实编辑器、版本化设计格式、无界面校验工具、示例、测试、文档和公开源码仓库。

第一版不实现：电流/电压模拟、单片机程序执行、校园网认证、云端账号、多人实时协作、内置大模型聊天、自动布线、PCB 设计、3D 外壳设计、自动生成制造级焊接板。允许人工规划后给出建议，不得把建议宣称为已验证的电气结果。

## 3. 第一版必须具备的功能

### 3.1 可编辑的面包板工作台

- 元件库、中央画布、属性面板、底部校验面板；画布是主要区域，不做营销页面。
- 新建项目；添加/删除面包板和元件；复制；平移；缩放；适应全部；选择；多选移动；90° 旋转；锁定对象。
- 两块 400 孔面包板可以沿长边或短边对齐拼接。几何拼接不会自动连通任何电源轨。
- 面包板要画出真实孔阵、a–j 标记、排号、中央沟槽、独立电源轨，以及对应型号存在的电源轨断点。不能用两个大矩形冒充面包板。
- 可切换连通高亮：选择一个孔，显示与它内部直接导通的所有孔；接线后可查看整个导通网络。
- 元件拖动时预览落脚孔、可占用空间和冲突；正式放置由同一套几何引擎计算。对真实尺寸型号不提供任意拉伸缩放。
- 显示模块遮挡的孔，并区分“被引脚占用”和“被板体遮挡”；底部引脚仍能通过同组外露孔引出。
- 不匹配任何面包板孔位的器件可放在板外，通过线缆连接，不能强行宣称插在面包板上。

### 3.2 连线

- 从明确的孔或可访问端子开始，到明确的孔或端子结束；悬空线只作为未完成草稿存在。
- 默认正交折线，可手动调整拐点、颜色、名称；支持选择与删除。
- 同时保存导线的电气端点和视觉路径。两条线在图上交叉不会自动导通；v0.1 使用孔/端子做连接点，不必支持任意导线上打结点。
- 支持沿面包板表面布置的硬跳线，以及抬高的软线示意；提醒走线跨越器件，但不假装完成三维碰撞分析。
- 显示估计走线路径长度，并说明未含插入深度、弯折和连接器余量。只有用户导入具体跳线套装长度时，才匹配套装规格。
- 撤销/重做包含拖放、旋转、拼板、接线、属性修改及 Agent 批量修改。

### 3.3 文件与图像

- 自动保存在当前浏览器本地；新建/导入替换前可恢复旧项目。发生存储失败时明确提示。
- 导入/导出 `.breadboard.json`；格式错误必须报告，不能静默丢失元件或线路。
- 导出 SVG 和 PNG：完整设计边界、孔号/针脚名开关、图例、未验证模型标识；不能截掉板边或长标签。
- “搭建模式”按线号逐根显示两端孔位/端子名称、颜色和前后步骤，可标记已完成。它只是指导，不代表实物已经导通。
- 附带“当前 ESP32 + OLED + 触摸键”和“双面包板环境节点”两个可编辑示例。

## 4. 元件库与真实程度

每个器件定义至少包含：唯一 ID、版本、名称、厂商/型号/转接板版本、外形尺寸、局部坐标原点、引脚坐标、安装方式、可接线区域、基本电气属性、原创渲染数据、来源链接和模型状态。

模型状态分开记录 `geometry_status` 与 `electrical_status`，可取 `verified`、`approximate`、`unknown`。这里 verified 只表示与注明的资料/实测吻合，不表示做过硬件认证。整颗元件不能因为知道芯片规格就被标成物理布局已验证。

首批范围：

| 器件 | v0.1 处理方式 |
| --- | --- |
| 400 孔面包板 | 至少一个明确的 30×10 接线区 + 100 电源孔配置；电源孔位置、轨道分段作为型号数据，不能仅凭“400孔/MB-102”推断实物结构 |
| XIAO ESP32-S3 Sense | 根据 Seeed 官方尺寸和引脚图建模；扩展板高度/占位、USB 方向与外接天线区域单独描述 |
| 当前双 USB-C ESP32-S3 N16R8 | 通用可配置开发板模板；未获准确外形及针脚坐标前显著标 approximate，不得套用不同 DevKit 的尺寸 |
| 0.96 OLED / 0.91 OLED | 标明具体转接板的四针顺序；未确定版本时使用可编辑占位，不能根据 SSD1306 芯片名推断外形 |
| TTP223 | 型号/转接板可配置；引脚与触发模式以资料为准 |
| SHT41、BMP390、LTR390 | 通用 I²C 模块模板 + 对应型号描述；未知转接板尺寸/针序明确待确认 |
| SEN66 | 根据官方模块尺寸建模，作为板外/支架固定的线缆器件；不假设它有能直接插面包板的 2.54mm 排针 |
| 电源模块 | 可配置的 3.3V 输出占位模型，额定/峰值能力必须显式填写或保留 unknown |

未知实物不阻止平台开发。先完成可靠的通用模板和未知提示，再允许用户导入更准确的器件定义；不要要求用户先把所有模块买齐。

不要直接复制 Tinkercad/Fritzing/厂商的图片、SVG 或元件库。v0.1 以原创矢量绘制为主；使用第三方资产必须确认再分发许可并保留归属信息。

## 5. 数据架构：设计文件是唯一事实来源

推荐 React + TypeScript + Vite；用 SVG 优先完成 v0.1 画布及导出，共享同一场景数据。如果实测 SVG 在目标规模有性能问题，再评估 Canvas/Konva，避免同时维护两个编辑器。

工程建议 pnpm workspace：

```text
apps/web/                 浏览器编辑器
packages/core/            几何、孔位、连通图、规则、事务；不得依赖 DOM/React
packages/schema/          版本化 JSON Schema、类型与迁移
packages/catalog/         元件与面包板定义、来源和许可
packages/render/          共享场景与 SVG 导出
packages/cli/             Agent 可用的命令行入口
examples/                 示例设计与正反例
docs/                     设计格式、建模、Agent 使用、计划与进度
```

选择当前相容的稳定依赖，提交锁文件。测试建议 Vitest + Playwright。生产站点 v0.1 是静态前端，无需数据库、API Key 或专用云服务；普通静态服务器即可运行。

所有入口遵守：

```text
画布动作 / 属性修改 / DSL 导入 / CLI patch
                 ↓
        Schema 校验 + 原子事务
                 ↓
       统一项目状态与撤销历史
                 ↓
   几何与导通图 → 规则检查 → 渲染/导出
```

关键建模约定：

1. 持久坐标采用整数微米，显示可用 mm；2.54mm 孔距表示为 2540µm。缩放和平移是视图状态，不改变实物尺寸。
2. 面包板、元件、引脚、孔和导线都有稳定 ID。显示名称变更不影响引用。
3. 器件包含带原点约定的局部几何；旋转变换同样用于外形、孔位吸附和碰撞检测。
4. 元件 pin-to-hole 映射由放置数据派生，不能让 DSL 自报一个与几何不一致的“已插入孔”。
5. 器件目录引用版本固定，必要时在导出的项目内嵌使用到的定义，避免升级元件库改变旧设计。
6. 区分 `net_intents`（希望哪些端点相连）与实际导通图；写下一个 SDA 网络意图并不会自动变出导线。
7. 电气规则不依赖导线颜色。内部电路不能一律当短路，电阻、LED、芯片引脚之间不进行无条件节点合并。
8. 未知 GPIO 配置、上拉、模块供电能力，输出 unknown/needs_review；不能当成通过或直接判错。

## 6. Agent DSL 与 CLI

第一版 DSL 使用声明式 JSON + JSON Schema 2020-12，扩展名 `.breadboard.json`；不急于发明自定义文本语法。Agent 可以可靠生成、校验、比较和修改，后续友好文本语法编译到同一结构即可。

设计文档至少包含：`schema_version`、`catalog_versions`、`metadata`、`boards`、`components`、`wires`、`net_intents`、`constraints`、可选 `view`。公开完整示例与字段定义。

下面是语义示意，不是要求实现者逐字照搬的完整有效文档；M1 必须产出可以实际解析的完整示例，替换这段示意：

```json
{
  "schema_version": "1.0",
  "boards": [
    {"id": "bb_a", "model": "breadboard_400@1", "position_um": [0, 0], "rotation_deg": 0},
    {"id": "bb_b", "model": "breadboard_400@1", "position_um": [0, 55000], "rotation_deg": 0}
  ],
  "components": [
    {"id": "collector", "model": "xiao_esp32s3_sense@1", "placement": {"board_id": "bb_a", "anchor_hole": "c3", "anchor_pin": "D0", "rotation_deg": 0}}
  ],
  "wires": [
    {"id": "w1", "from": {"hole": "bb_a.a7"}, "to": {"hole": "bb_b.a7"}, "color": "green", "waypoints_um": []}
  ]
}
```

孔名、边轨地址、旋转方向、端子类型均须正式定义。上例里的孔位只是说明引用方式，不能作为真实 XIAO 接线图。400 孔常用 30 排，不能出现前面聊天里 `row_36` 这样的无效例子。

Agent 必须能通过 CLI 完成：

```bash
pnpm bb catalog list --json
pnpm bb catalog inspect xiao_esp32s3_sense@1 --json
pnpm bb inspect examples/environment_node.breadboard.json --json
pnpm bb validate examples/environment_node.breadboard.json --json
pnpm bb connectivity examples/environment_node.breadboard.json --from bb_a.a7 --json
pnpm bb apply design.breadboard.json --patch edits.json --dry-run --json
pnpm bb apply design.breadboard.json --patch edits.json --out revised.breadboard.json
pnpm bb export revised.breadboard.json --format svg --out layout.svg
pnpm bb steps revised.breadboard.json --json
```

CLI 是上述能力的建议契约，实际命令可微调，但功能不能删掉。JSON 输出稳定，错误退出码非零；规则结果提供 `severity`、`code`、相关对象/端点 ID、原因、建议。明确区分 schema/几何非法、电气问题和未知证据。

`apply` 使用结构化领域操作，至少覆盖 add/remove/move/rotate component、add/remove board、add/remove/update wire、update property。一次补丁原子执行：结构非法时全不应用；电气问题可留在草稿中但显著报告。基于 revision/hash 防止覆盖并发修改。网页和 CLI 调用同一事务引擎。

不通过 eval 执行 DSL，不允许设计文件携带任意脚本。v0.1 不需要搭建 Agent 服务器或 MCP；提供 CLI 文档，另一个会话就能直接工作。

## 7. 规则引擎与校验边界

必须实现并用反例验证：

| 类别 | 必须检查 | 不得宣称 |
| --- | --- | --- |
| 格式 | 重复 ID、未知引用、无效排号/孔号、不支持版本、非法坐标 | 解析成功等于电路正确 |
| 放置 | 插针与孔阵匹配、同孔占用、明确高度层的实体碰撞、放在电源轨造成引脚互短 | 未知转接板也能精确吸附 |
| 面包板 | 同排五孔导通、中央沟槽隔离、电源轨分段、两块板互不自动导通 | 红蓝印线就是电气连接证据 |
| 导线 | 端点存在、悬空、几何路径更新、交叉不相连 | 线条视觉碰到即连接 |
| 网络 | 期望网络断开、明确供电对地短接、明确不同电压源直接并联、缺少公共参考地 | 算出真实电流或器件运行结果 |
| 接口 | 在配置明确时检查信号电平、方向冲突、同一实际 I²C 总线上的重复固定地址 | 所有输出引脚默认正在输出；全局重复地址就是冲突 |
| 证据 | 未验证尺寸/针序/电气数据、未知电源余量列入 needs_review | 没报 error 就能安全上电 |

I²C 地址冲突仅在器件确实共享同一 SDA/SCL 连通总线且地址配置明确时报告；不同控制器的隔离总线可以使用相同地址。开漏输出与推挽输出分别建模。

SEN66 电源是规则示例：不能仅看平均约 90mA 就判“足够”；需结合峰值、电源余量和模块实际规格。也不能硬编码“所有 XIAO 都禁止为它供电”。官方资料给出的 3V3 标称能力不等于每一种组合已实测稳定，缺少证据时保留审核项。

## 8. 界面与可用性标准

- 桌面优先，普通笔记本可用，支持触控板缩放/平移，浏览器页面不得被画布手势意外滚走。
- 适度真实的原创矢量外观：面包板孔、沟槽、塑料边框、模块板体、排针、USB 外形清楚；高倍缩放可读 GPIO、孔名与端子名。不能只是通用流程图方块。
- 未验证器件显示可见徽标；板外器件有明确的线缆连接提示。
- 所选孔的连通组、所选导线的两端、校验错误的位置都有明显高亮。
- 屏幕操作应有文字/键盘替代路径；颜色配合文本和线号，不单靠红绿区分。
- 编辑器中的 DSL 面板允许编辑草稿、校验、显式应用。错误草稿不破坏当前画布；画布修改同步回设计文档，避免双向编辑相互覆盖。
- 项目菜单具备新建、示例、导入、导出；本地保存状态可见。界面文案不显示内部堆栈。

## 9. 实施顺序与阶段验收

每阶段结束更新 `docs/STATUS.md`：已完成、验证结果、限制、下一步；不要用更新文档代替实现。

### M0：独立项目与最小运行环境

- 建立工程、MIT 许可证草案、基础脚本与 CI 骨架。
- 确定孔位命名、单位、坐标原点、旋转规则、轨道定义；写入 `docs/ARCHITECTURE.md`。
- 验收：干净安装后能启动空工作台；实现和 README 命令一致。

### M1：先让 Agent 能生成有效设计

- Schema、目录格式、面包板孔位生成、放置变换、物理连通图、事务与基础 CLI。
- 完成一个含两板、模块和真实线端点的有效示例，以及短路/断路/无效孔位反例。
- 验收：不打开浏览器，CLI 可校验、修改、查询网络并生成 SVG；执行失败不能留下半修改文件。

### M2：完成真正的面包板画布

- 面包板与器件渲染、缩放平移、落脚孔吸附、摆放/旋转/复制/删除、多选、锁定、孔占用提示。
- 验收：两块 400 孔板可拼接；放置、移动和旋转后的 pin-to-hole 映射与高亮一致；不重现“板体挡孔但平台认为能插线”的误导。

### M3：手工连线与校验闭环

- 接线、折线编辑、色彩和线号、实际导通图、规则面板、点击错误定位、网络高亮。
- 验收：五孔组、沟槽、分段电源轨、跨板跳线都正确；制造错误再修复，警告同步出现/消失。

### M4：保存、导出、DSL 和搭建模式

- 本地保存/恢复、导入/导出、DSL 编辑应用、撤销/重做、SVG/PNG 和逐线搭建步骤。
- 验收：刷新浏览器和文件往返不会丢失设计；非法 DSL 不污染画布；导出内容完整清晰。

### M5：实用示例、性能与体验

- 当前桌面设备与未来环境节点示例，按模型证据状态标注。
- 扩展器件 JSON 导入，指导贡献者不用修改应用逻辑就添加一个简单模块。
- 用至少四块 400 孔板、20 个模块、100 根线做可重复性能检查，记录环境与结果；修复明显拖动卡顿，不为了指标提前重构。
- 验收：用户在干净浏览器按 README 能完成摆两板、放元件、接线、定位一个错误、导出、重新导入；Agent 可对同一项目完成同样修改。

### M6：开源准备与发布

- 中文 README + 简短英文介绍，清楚写明功能、安装、示例、限制、DSL/CLI 用法、路线图。
- 补齐 CONTRIBUTING.md、SECURITY.md、LICENSE、THIRD_PARTY_NOTICES.md、元件资料来源、问题模板。
- 提交依赖锁文件；CI 跑 typecheck、单元测试、构建和关键浏览器流程。
- 原创示例和真实产品截图；截图不能带账号、校园网凭据或其他项目页面。
- 发布流程见第 11 节。

## 10. 必须覆盖的关键测试

不要只测试“能打开网页”。至少包括：

1. 面包板 `a7–e7` 连通、`f7–j7` 连通，两组和第 8 排互不连通；声明断开的轨道确实断开。
2. 仅拼接第二块板不会产生电气边；加跳线后才连通，删除后断开。
3. 导线交叉不连通，同一明确端点连接才导通；移动端点所属器件后没有隐形旧连接。
4. 四次 90° 旋转回到原始 pin-to-hole 映射；不合法落脚、同孔插两针有明确结果。
5. 把电源与地直接短接能报出相关端点；未知电气属性不能给“验证通过”的假绿灯。
6. 相同 I²C 地址处在同一总线报冲突、隔离总线不报；可配置地址在修改后重新校验。
7. JSON 往返保留稳定 ID、坐标、线端点与目录版本；错误引用、超范围孔位、过新版本被拒绝。
8. 批量修改原子性、revision 冲突、撤销/重做，以及 UI/CLI 的连通与校验结果一致。
9. 浏览器完成拖放→接线→出错→修复→导出→导入→刷新恢复；验证真实状态而非只截一张图。
10. SVG/PNG 导出没有裁切；孔号、标签、未验证徽标与界面一致。

## 11. GitHub 开源发布流程

用户期望最终源码提交到其 GitHub 并开源。执行时使用可用的 GitHub 工具或官方 `gh` CLI，读取当前认证账户；若未认证，先把本地产品、提交和文档完成到可审阅状态，再请求用户登录。

1. 在独立新项目建立 Git 仓库，按阶段提交，禁止 force push。不要在原 ESP32 目录运行 `git add .`。
2. 默认仓库 `breadboard-studio`。若账户下已存在同名仓库，先只读检查，不能覆盖未知远程历史；目标无法确定时询问用户。
3. 完成全部必需测试、构建、许可核对以及待发布文件/历史中的秘密检查；不能只靠 `.gitignore` 就宣称没有泄露。
4. 按用户的开源意图创建/使用正确的公开仓库，添加清楚描述、README 和 MIT LICENSE，推送代码。
5. 配置 GitHub Actions 和静态 GitHub Pages 演示；正确处理仓库子路径、资源路径和路由刷新。无需付费域名。若 GitHub 账户权限/Pages 条件阻塞，源码发布与本地运行应仍可交付，并明确报告线上演示的阻塞。
6. 检查远端默认分支与提交一致、CI 结果，以及实际部署 URL 能加载示例并运行关键流程。确认成功后创建 v0.1.0 标签/Release，写明已实现功能和已知限制。
7. 最终交付：仓库 URL、提交哈希、可用演示 URL、启动命令、CLI 示例、测试结果摘要、尚未验证的模块与功能。不能伪造 GitHub/部署链接，不能把仍在运行的 CI 说成通过。

公开仓库不自动等于明确授予开源使用许可，因此必须实际包含 LICENSE。第三方元件/图片许可单独核对，不被项目 MIT 许可证自动覆盖。

## 12. Goal 的完成条件

只有满足以下条件才可宣布 v0.1 完成：

- 新安装环境能按 README 启动真实可编辑的平台。
- 两板摆放、元件、连线、规则校验、文件保存/往返、SVG/PNG 导出、逐线搭建模式都可用。
- Agent 不操作浏览器，也能查询元件、读写设计、批量修改、校验、查询导通与导出。
- UI 和 CLI 共用数据/规则；关键正反例测试通过。
- 未验证模型可见且可配置；仿真/自动布线等未实现能力没有伪装成已实现。
- 公开 GitHub 仓库及开源许可证已落实；如外部权限阻塞，报告完成部分和精确阻塞，不能宣称整个目标完成。
- 在线演示可访问，或明确记录账户/权限导致的部署限制并给出本地可运行交付。

不要以“已经做出一个好看的界面”“写好了计划”“只剩后面的小功能”提前结束。反过来，也不要为了非第一版功能无限扩张。
