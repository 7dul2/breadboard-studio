# 阶段 5 RFC：真实固件后端

> 状态：**已调查，建议不做**（2026-09-09）
> 计划 §14.2 要求「先写 RFC 与技术验证」再决定是否接入 `SimulationBackend`。这就是那份 RFC。

## 1. 结论

三条路线都调查了，结论是：**阶段 5 交付不了它自己的标题，而且这不是排期问题，是结构问题。**

| 路线 | 判定 | 一句话 |
| --- | --- | --- |
| ESP-IDF QEMU 编译到 WASM | **否决** | 这个项目赖以存在的两个外设——GPIO 与 I²C——在 ESP32-S3 机器里恰好都不存在，而且是政策不是积压；另有 GPL-2.0 与本仓库 MIT 的许可证冲突 |
| WASM/JS 里的指令集模拟器 | **唯一能满足接口的，但地基是一个 2.5 周新、1 star 的仓库** | 值得花两周做一次**一次性验证**，不值得当项目做 |
| WebSerial 接真板 | **重新归类**：它不是仿真后端，是另一个功能 | `SimulationBackend` 十个方法里有五个它给不了；但作为「烧录 + 看串口 + 硬复位」它一周就能做出来 |

**建议：把阶段 5 标记为「已调查并谢绝」，把 WebSerial 作为一个诚实命名的独立功能另开卡。** 这是一个合法的结局，不是失败——计划要求的就是先验证再决定，验证的结论可以是「不做」。

## 2. 为什么它交付不了自己的标题

一句话：**浏览器里没有任何东西能编译 Xtensa。**

LLVM 的 Xtensa 后端至今是 Espressif 的树外分支，ESP-IDF 的构建是 CMake + Python + Kconfig。所以「真实固件」在浏览器里只能是「别人已经编译好的 `.bin`」。

于是问题变成：谁会用它？

- 手上有 `.bin` 的人，就有工具链；
- 有工具链的人，就有板子和 `idf.py monitor`，不会跑到浏览器里的面包板图上调驱动；
- 剩下的受众是**没法编译固件的人**——而他们没有任何东西可以拿来运行。

这个论证没有被三份调查报告里的任何一条推翻。

约束 6（既有功能不得回退）让情况更糟而不是更好：QuickJS 后端必须继续工作，所以阶段 5 不替换任何东西，而是在一个能用的后端旁边**再加一个更慢、更不完整、且不能编辑程序的后端**。已经做完的每一个功能——断点、时间线、录制回放、属性滑杆、宿主器件渲染、10× 倍速——都需要两份诚实的实现，而其中一份做不到 10×、映射不到源码行、并且对任何未建模的外设都会静默地「成功」。

市场证据异常干净：**四个资源远比我们多的主体，各自独立得出了同一个结论**——浏览器里跑带可用外设的 Xtensa，要么是服务端问题，要么是闭源产品。Velxio（2777 star，Espressif 列为硬件伙伴）把 ESP32 跑在**服务端 Docker 里的 QEMU** 上，其 README 原话如此；Wokwi 以 MIT 开源了 avr8js 和 rp2040js，却从未发布 ESP32 核心；Cirkit 花了一个小团队约八个月，结果闭源；Espressif 自家的 esp-emulator 按既定政策**只做 RISC-V**。

## 3. 三条路线的判定

### 3.1 ESP-IDF QEMU → WASM：否决

浏览器里跑 QEMU 本身**是可行的，且已被现场验证**：`ericmigi/pebble-qemu-wasm` 从 GitHub Pages 启动真实裸机固件，靠 `coi-serviceworker` 拿到跨源隔离（`crossOriginIsolated === true`，wasm 9,241,128 B，brotli 后 1,994,658 B）。

死在 ESP32-S3 那一半。以下两条我**亲自拉源码核实过**：

- `hw/gpio/esp32_gpio.c` 全文 109 行，写处理函数字面上是空的：
  ```c
  static void esp32_gpio_write(void *opaque, hwaddr addr, uint64_t value, unsigned int size)
  {
  }
  ```
  读处理只回答 `A_GPIO_STRAP`，其余一律返回 0。
- `hw/xtensa/esp32s3.c` 全文 1002 行，实例化了 26 个外设（aes、gdma、gpio、rng、rsa、sdmmc、spi1、systimer、timg0/1、twai……），**其中没有 I²C**。文件里仅有的两处 `i2c` 是一个 include 和一句指向 *ESP32*（非 S3）机器初始化函数的注释。

也就是说，这个项目整个建立其上的两个外设，恰好是这条路线上不存在的两个。而且这是**政策不是积压**：Espressif 的 issue #37 自 2022-03-20 开着，igrr 明确表示「我们不能承诺自己实现这个功能」。

另有两个独立的否决理由：

- **许可证冲突。** QEMU 是 GPL-2.0-or-later，本仓库 `LICENSE` 是 MIT，`THIRD_PARTY_NOTICES.md` 明确写着依赖「均为 MIT 或兼容的宽松许可证」。C 桥接层、GPIO 矩阵、以及任何被搬进 QEMU worker 的宿主器件模型，都会落到 copyleft 一侧。（这条我核实了本仓库这一半。）
- **版本鸿沟。** Espressif 的分支基于 QEMU 9.2.2，而 Emscripten 宿主支持是 QEMU 10.1 才合入上游的。要先把 Espressif 的补丁集 rebase 到 ≥10.1。

### 3.2 指令集模拟器：唯一能满足接口的，但地基很薄

没有现成的、许可证兼容的、浏览器端 ESP32-S3 ISS 可以直接拿来用：Wokwi 的 ESP32 核心闭源，Cirkit 的 Rust/WASM S3 核心闭源，Velxio 是 AGPL 且实际跑在服务端 QEMU 上。

唯一可用的开源起点是 `realhidden/m5webassembly` 的 `lib/xtensa`——**一个建库与最后一次推送都在 2026-08-22 的仓库，1 star，0 fork，286 kB**。它自己的 README 把模拟器称为「把 sketch 重编译成 WebAssembly」之外的**兜底路径**，文档里写着「没有 SPI-LCD、I2C 或 I2S 模型，所以任何视觉或听觉的东西都无法工作」。

这条路线真正的优点有两个，都很实在：

- **不引入第二个 wasm。** 约 176 kB 原始 JS、约 25 kB gzip，进现有的惰性 worker chunk。`check-dist.mjs` 的「wasm 恰好一个」规则与 900,000 B 入口闸门都不受影响。
- **宿主那一半完全不用改。** `digital-net.ts`、`i2c.ts` 和 S4.x 的每一个器件驱动，都不关心总线上的流量来自 QuickJS 还是来自固件的寄存器写入。

### 3.3 WebSerial：不是后端，是另一个功能

`SimulationBackend` 的十个方法里，这条路线给不了五个：`pause`、`step`、`reset`（虚拟时间意义上的）、`setSpeed`、`setBreakpoints`——因为**没有时钟可驱动，也没有办法在网络跳变处停住一颗真实 MCU**。确定性和录制回放同样给不了。

它**绝不应该**被注册成一个 `SimulationBackend`。

但把它当成它本来的样子——「烧录一个 `.bin`、看真实串口、按一次真实复位」——它是三条路线里唯一一周内能交付真实价值的：不需要服务端、不需要安装、不需要 wasm，建立在 Espressif 自家五周前还发过版的 esptool-js 上。

必须一并说清的限制：真板的 GPIO 接的是真元件，**应用里模拟的 OLED 和传感器根本不在那个电路里**。以及浏览器支持：Chrome/Edge 有，Firefox/Safari 没有，不支持的浏览器上要明说而不是让按钮静默失效。

## 4. 如果仍然要试：分阶段，每阶段带终止判据

裁判给的计划，每个阶段的**终止判据**（什么观察结果会让这次尝试结束）比目标更重要：

| 阶段 | 目标 | 终止判据 |
| --- | --- | --- |
| 0（半天） | 就是这份 RFC | 写完之后如果觉得剩下的问题不值两周，就停在这里 |
| 1（约 3 天） | 在 `packages/` 之外的一次性 harness 里 vendor 那 10 个文件，跑一段**自写的裸机**循环，同一输入两次比特一致 | 撞上未实现指令 / 两次运行不一致 / 读了一天说不清这十个文件各自在做什么 |
| 2（约 1.5 周） | 把 GPIO(0x60004000) 与 I2C0(0x60013000) 的 MMIO 桥到 `digital-net.ts` 和 `i2c.ts` | I²C 控制器寄存器模型无法在约 500 行内满足真实驱动的命令列表用法；或桥接必须改造 `i2c.ts` 的事务级计时才能同步 |
| 3（约 1 周） | 进真实 Worker 与生产构建，固定量子，`nowUs` 改整数微秒累加 | 持续忙循环比率低于约 0.2× 实时——那时「1×」就是谎话，10× 更不可能 |
| 4（硬性 3 周） | 启动一个钉死版本的 ESP-IDF v5.4 镜像走到 `app_main` | 三周到了还没走到 `app_main`；或 ROM stub 的尾巴明显不收敛（引擎自带 49 个 stub，对 2238 个已知 ROM 符号） |
| 5（约 1.5 周） | 才开始接 `SimulationBackend` | **写不出一份读起来不像「劝人别用」的限制说明** |

阶段 5 的终止判据值得单独抄一遍，因为它是这个项目一贯的判断方式：如果对这个后端的诚实描述难看到你自己都不愿意把它放进界面，那答案就已经有了。

## 5. 建议改做的

1. **把 WebSerial 作为独立功能另开卡**，名字里不带「仿真」二字。它做的是「把固件烧进真板、看它的串口」，与仿真器并列而不是冒充仿真器。惰性加载（约 213 kB 原始，直接进主包会把 740,450 B 顶到约 953 kB，越过闸门）。
2. **把这份 RFC 的结论写回计划 §14.2**，让「已调查并谢绝」成为记录在案的状态，而不是一个悬着的待办。
3. 如果哪天 `espressif/esp-emulator` 的 issue #5（外部设备接口 SPI/I2C/GPIO 桥）有了回应，或它开始支持 Xtensa，这个判断值得重做——那是唯一可能出现官方路径的地方。

## 6. 待解问题（若重启此题需先回答）

- 引擎真实速度到底是 README 说的「约 0.6× 实时」还是实测的 33 MIPS（约为 240 MHz 核心的 0.07×）？两者只有在「虚拟时间在空闲的 FreeRTOS 上快进」的前提下才能自洽。
- `i2c.ts` 现在的事务级位时计时（400 kHz 下 29 bit = 73 µs，到期原子提交）能否与一个被固件轮询的寄存器级 I²C 控制器共存，还是计时必须整体搬进控制器？
- 两个后端、两套互不兼容的程序模型，共用一个「搭建/仿真」开关，界面该怎么说？这是产品问题，不是工程问题。
- 录制文件在引擎版本不同时，是否需要**硬拒绝**而不只是提示？S4.5 目前对「来自另一版设计」的录制是刻意放行加提示的。
